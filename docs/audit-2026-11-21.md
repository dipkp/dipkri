# dipkri — full audit (web · desktop · android)

Date: 2026-11-21 · Branch: `sec/api-hardening` · Method: code read + jar/API inspection + live probes
Everything below was verified in the code or against production; items marked *(needs device test)* require a phone.

---

## 1. Executive verdict

| Platform | Score | Why |
|---|---|---|
| Web | **5/10** | Feature set is real and the security pass landed, but permissions are missing, sync is coarse (1 s, all-to-all), and there is dead code and bloat. |
| Desktop | **5/10** | Phase 2 works (verified 206 + cache wipe), but it ships unsigned, has no auto-update, no crash reporting, and one window only. |
| Android | **3/10** | It launches and logs in now, but the local HTTP server is single-threaded, background playback is unproven, and there is no release signing. |

**Top 3 risks**

1. **Any participant can take over playback.** `CMD:play/pause/seek/playbackRate/loop/host` only check `validateLock()`, which is `!this.lock || socket.uid === this.lock` (`server/room.ts:230-232`). With no room lock, that is *everyone*.
2. **Android streaming will stall under real use.** `LocalHttpServer` accepts and handles requests on one thread (`android/.../LocalHttpServer.kt:38-49`); a single open stream blocks `/health` and every seek that opens a second connection.
3. **Shipping blind.** Debug-signed APK, no crash reporting, no version check; a bad build is indistinguishable from a bad phone.

## 2. Issues

### P0 — broken / critical

**P0-1 · Any guest can control or replace the room video**
`server/room.ts:266-287` (`CMD:host`, `CMD:play`, `CMD:pause`, `CMD:seek`, `CMD:playbackRate`, `CMD:loop`), guard at `server/room.ts:230-232`
- *What:* the only check is "room is locked to this uid". Unlocked rooms (the default) accept these events from any socket.
- *User impact:* a stranger who joins with the code can pause the film, jump to the end, change speed, or swap the video for everyone — indistinguishable from a bug.
- *Fix:* record the controller uid (there is already a `controller` concept and `CMD:changeController`) and reject if `socket.uid !== this.controller && socket.uid !== owner`. Until then, at minimum require `socket.uid` (signed-in) — login is now mandatory anyway.

**P0-2 · Android local server is single-threaded**
`android/app/src/main/java/org/dipkri/app/LocalHttpServer.kt:38-49`, `LibtorrentEngine.serve` (`LibtorrentEngine.kt:180+`)
- *What:* `while (running) { handle(server.accept()) }` handles each connection inline, and `serve()` blocks until the whole range is written. ExoPlayer opens a second connection for every seek/metadata probe.
- *User impact:* play works, then the first seek hangs the player and `/health`; a second tab can deadlock the app's streaming entirely.
- *Fix:* `val socket = server.accept(); thread { handle(socket) }`, and cap concurrent streams (2-3) with a semaphore.

**P0-3 · Room passwords and capacity are dead when Postgres is absent**
`server/room.ts:115-137`
- *What:* both checks live inside `if (postgres)`. Production has `DATABASE_URL` empty, so a password-protected room is joinable by anyone with the code, and there is no per-room user cap.
- *User impact:* users believe a password protects the room; it does not. A room can be flooded.
- *Fix:* keep the password/owner in the in-memory room object (set at create) and enforce it in the middleware without Postgres.

### P1 — UX, sync, alignment

**P1-1 · Sync traffic grows quadratically**
`server/room.ts:100-113` (broadcast every 1 s to everyone), `src/components/App/App.tsx:1511-1517` (every client emits `CMD:ts` every second)
- *What:* N clients → N emits/s → N×N deliveries/s, plus each client runs a rate-correction pass (`App.tsx:1342-1360`).
- *User impact:* on a 1 GB VM, ~40 viewers causes jitter and CPU spikes; playback speed wobbles as corrections fight.
- *Fix:* send the map at 2-3 s, only to clients whose delta exceeds a threshold, and only when values changed.

**P1-2 · Late joiner has no authoritative "now"**
`src/components/App/App.tsx:1507` (`REC:getRoomState`)
- *What:* state comes from the requesting socket's own `videoTS`, not from the server clock.
- *User impact:* a viewer who joins mid-film can start 10-30 s off and then drift-correct visibly.
- *Fix:* answer with `videoTS + (now - pausedAt)` computed server-side.

**P1-3 · Mobile had no way to end a room** — fixed today (`src/components/App/App.tsx:3606+`, floating "End party"). Still worth noting: the new pill is ~34 dp tall, below the 48 dp touch-target minimum.
- *Fix:* `padding: 12px 18px` and `minHeight: 48`.

**P1-4 · Dead mobile UI**
`src/components/Mobile/MobileEnhancements.tsx:177` (`MobileTabBar`) and its 6.4 KB CSS are imported (`App.tsx:101`) but never rendered.
- *User impact:* none directly, but it explains why mobile controls feel missing; the bottom tab bar users expect does not exist.
- *Fix:* render it (it is already written) or delete it.

**P1-5 · Android popup is a full-screen Dialog with no chrome**
`android/.../MainActivity.kt:60-100`
- *What:* Google's consent page opens inside a bare `Dialog`, no title bar, no close button, no URL.
- *User impact:* if the flow stalls the user cannot back out; on a notch device the top of the page sits under the cutout.
- *Fix:* add a title bar with a close button and apply `WindowInsets` padding.

**P1-6 · Background playback unproven**
`android/.../TorrentService.kt` (foreground service exists) but the WebView `<video>` pauses when the activity is backgrounded.
- *User impact:* locking the phone stops playback even though the service keeps downloading.
- *Fix:* verify on device; if it pauses, either accept it in the copy ("keep the screen on") or move playback to ExoPlayer in the service.

### P2 — AI bloat / cleanup

**P2-1 · Duplicated torrent-title cleanup**
`server/room.ts:714-718, 790-794, 834-838` and `server/server.ts:392-396` repeat the same four `.replace()` calls.
- *Fix:* one `cleanReleaseName()` in `server/utils/regex.ts` (that file already exists).

**P2-2 · Two engines, one behaviour**
`desktop/sidecar.mjs` and `android/.../LibtorrentEngine.kt` re-implement the same policy (idle sweep, magnet-only, range). Nothing keeps them in step.
- *Fix:* document the contract in one place (the endpoint table already exists) and add a shared checklist to `docs/`.

**P2-3 · Console noise in the client**
10 files call `console.log`; `App.tsx` alone logs playback and YouTube internals.
- *Fix:* a `debug()` helper behind `import.meta.env.DEV`.

**P2-4 · `server/server.ts` still carries VM/browser/Stripe code paths that production never uses** (`VBROWSER_*`, `DO_*`, `HETZNER_*`, `checkoutSub`, `manageSub`).
- *Impact:* ~400 lines of attack surface and startup work that never runs (all env vars are empty).
- *Fix:* gate behind a feature flag or delete; this alone shrinks the security surface you have to defend.

**P2-5 · Duplicate dependency pins** — `desktop/package.json` pins `uint8-util@2.2.5` to work around a webtorrent bug; nothing notes when it can be dropped.
- *Fix:* add the upstream issue link where the pin lives.
